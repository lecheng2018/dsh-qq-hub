## 1. 队列规则

当前状态：**M0 五项已完成，G0 已放行；M1 是下一阶段且尚未开始。** G0 放行只允许进入 M1，不代表真实环境或生产操作获批。

- 硬门禁为 `M0 → M1 → M2 → M3 → M4 → M5 → M6`；未通过阶段门禁不能把后续任务标为完成。
- `→` 表示前置依赖和串行推进；同一缩进层的 `├─` 表示在依赖满足后可并行；`[Gx]` 表示阶段放行门禁。
- 纯模块、适配器和测试只能在自己的文件范围内并行；共享契约、package/workflow、host/hub、开关、持久化和发布操作按任务书的唯一 owner 串行。
- `src/host.js`、`src/host/**`、`src/chat/hub.js`、`src/kernel/legacy-fallback.js` 同一时刻只允许一个 Integration 接线 PR。当前导出的 `src/host/pipeline.js` 是接线定位点，不按旧版 host 行号操作。
- 所有新主链先 default-off；任何失败都停留在当前已验证节点，不能用减少场景、放宽断言或恢复暂停版 aggregator 过门。
- M5 的真实 DSH、真实 OneBot、生产配置、服务重启、实发和流量扩大都需要 owner 当阶段批准；任何时候不允许两个真实写者。
- 每个节点进入队列前要有固定基线/依赖证据；离开队列时补命令、退出码、测试数、包/sha256、未验证项和回滚实测。没有证据就标为 `blocked/未验证`。

## 4. M1 队列：文档/测试可并行，host/hub 修复严格收敛

### 4.1 并行准备

在 `[G0]` 通过后，以下准备工作可分别由角色并行：

```text
M1-A 面板安全测试准备
M1-B backfill 行为测试
M1-C unknown/媒体 fallback 测试
M1-D 文档与实际能力核对
```

M1-A/B/C 若需要源码修复，不能按准备工作的并行关系同时改 host/hub。M1-D 没有任务书额外依赖，但仍受 G0 阶段入口约束。

### 4.2 唯一 host/hub 集成窗口

```text
M1-A host/面板修复
      ↓
M1-B backfill 接线/修复
      ↓
M1-C legacy 发送/媒体修复
      ↓
M1-E 开关默认值、读取时机与回滚复核
      ↓
[G1]
```

- M1-A/B/C 的纯测试、文档和不触及共享接线的独立修复可在各自任务内进行；进入 `src/host.js`、`src/host/**` 或 `src/chat/hub.js` 时，必须等待上述唯一窗口。
- M1-E 统一检查 flag-off 基线、非法值 fail-closed、`FLAG_INGRESS_AGGREGATOR` 默认关、memory takeover 默认关和不双发；不能在 M1 阶段扩大灰度。
- G1 仅在风险有复现/修复或接受结论、backfill/unknown 行为测试、真实能力文档和安全开关姿态均有证据后放行。

## 7. M4 队列：唯一主链接线队列

M4-0～M4-6 不并行开多个接线 PR，严格按以下顺序：

```text
M4-0 组装根 + 单一 FLAG_MODULAR_CORE（default-off）
  → M4-1 私聊纯文本全链
  → M4-2 群聊/命令/回合控制
  → M4-3 媒体/真实回执/失败路径
  → M4-4 backfill/后台/主动消息统一收口
  → M4-5 manifest 驱动的可插拔模块接线
  → M4-6 全量 fake 集成、500 例、三态对比、回滚
  → [G4]
```

每一步的额外依赖和停止条件：

| 顺序 | 依赖 | 必须保留的边界 | 失败时 |
|---|---|---|---|
| M4-0 | G3 | host 只增加组装；旧路径完整保留；flag-off 等价 | 关闭开关/回退代码，停在 G3 交付物 |
| M4-1 | M4-0、M3-A/B/C/D | Inbound→Session→Turn→Context→Outbox 全链；只创建一个 session；无 legacy 直发 | flag-off，修复退回对应 Core/adapter 工作流 |
| M4-2 | M4-1 | 群权限、命令幂等、合流、取消和审批不减场景 | 保持上一切片，不推进媒体接线 |
| M4-3 | M4-2 | queued/sent/unknown 不混淆；发送后超时不重发 | 关闭新核心，保留 unknown 审计 |
| M4-4 | M4-3、M3-F 对应模块 | 实时/backfill/后台/主动消息共用统一入站/出站契约；无物理发送旁路 | 关闭新核心，登记未收口来源 |
| M4-5 | M4-4、M3-F（M3-E 当前不适用） | host 只按 manifest 装配；任一当前适用的 optional 模块可禁用/失败/卸载；不要求恢复 pet | 回到 M4-4，模块不阻塞核心聊天 |
| M4-6 | M4-1～M4-5 | 全量测试、500 例、数据兼容、重启、模块组合和 flag-on→off 回滚 | 保持 default-off，不进入 G4 |

G4 放行后才可安装固定工件并进入 M5；不得用 fake 全绿替代真实环境验证。

## 8. M5 队列：固定工件和 owner 批准的真实环境顺序

```text
[G4]
  → M5-1 固定 tgz/sha256 的隔离安装
  → M5-2 真实 DSH + fake OneBot
  → M5-3 真实 OneBot dryRun（owner 批准）
  → M5-4 owner 私聊实发
  → M5-5 一个测试群，再进入其他既有群并冻结观察
  → M5-6 回滚实测
  → [G5]
```

为避免把流量扩大和稳定观察混为一次成功回复，M5-4 之后按以下串行放行：

1. owner 私聊场景完整通过，才进入一个测试群。
2. 测试群完整通过，才申请其他既有群；不并行扩大。
3. 进入批准范围后冻结工件、配置和模块集合，完成 M5-5 的稳定观察。
4. 在 G5 前完成 M5-6，实际验证新核心→legacy/上一工件、唯一连接、会话可见性、数据读取和恢复时间。
5. 任意重复发送、串话、越权、不可恢复断线、P0/P1 或证据缺失，立即停止扩量并按影响范围 dryRun/回滚；不删除异常证据。

M5-3 及以后每一节点都必须有 owner 当阶段批准；生产 owner 尚未批准时，队列停在上一节点。
