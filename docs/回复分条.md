# 回复怎么分条（调研 + 最终口径）

一次模型回复要不要拆成几条 QQ 消息发，看起来是小事，做错两种都难看：

- 按字数一刀切：句子被切在半截，「到14:22」变成「…到14」+「22 已经烧掉 55%」。
- 把模型的每个换行当消息边界：一段排版正常的指标汇报被拆成「4 条极短 + 1 坨巨块」。

2026-11-05 读了两份真实实现（都是开源、都在线上跑群聊），结论写在下面，代码在
`src/chat/reply.js`（`segmentUnits` / `mergeUnits` / `segmentBubbles` / `capBubbles`）。

## AstrBot

`astrbot/core/pipeline/result_decorate/stage.py`、`astrbot/core/config/default.py`。

- **不按换行切**。切分正则 `.*?[。？！~…]+|.+$`，只认句末标点，而且标点跟着前一句走。
- **整段太长就干脆不分**：`words_count_threshold`（默认 150），超过阈值整条发出。
- 分条默认是关的（`enable: False`）。
- 条与条之间停顿：`interval` 默认 `1.5,3.5` 秒随机；`log` 模式按字数取对数，短句发得快。
- 只切纯文本组件，图片、语音、表情不动。

## MaiMBot（麦麦）

`src/chat/utils/utils.py` 的 `_split_into_sentence_segments`、`_merge_processed_segments_to_max_count`，
另有一份 `src/chat/utils/llm_sentence_splitter.py`。

- 切点：`，` `,` 空格 `。` `;` 换行；但带一串守卫条件：
  - 引号、书名号内部一律不切；
  - 标点紧挨冒号（`：` `:`）时不切；
  - 空格两侧都是字母或数字时不切（英文句子、数字单位）；
  - 破折号附近不切。
- **概率合并**：按原文长度定 `split_strength`（<12 字 0.2，<32 字 0.6，更长 0.7），
  `merge_probability = 1 - split_strength`，相邻段按这个概率合并 —— 短回复更容易连成一条，
  长回复更容易真的分开，目的就是不要机械感。跨换行的段不参与合并（换行是排版意图）。
- **条数上限用均匀分组**：`_merge_processed_segments_to_max_count` 把段均分成 `max_count` 组，
  而且把被合并各段原本的分隔符补回去，避免多句硬拼成没有标点的一坨。
- 高级模式：再调一次模型做语义断句，严格校验「只动切分位置、不改一个字」，
  校验不过就报错而不是照发；模型判断不需要拆时返回 `no_split`。

## 我们的口径

1. **硬边界**：`|||`（她自己划的）、空行（段落）。这两个一定成条。
2. **句末标点**：`。！？!?…；;`。守卫照 MaiMBot 抄：引号内不切、紧挨冒号不切、
   数字中间的 `.` 不切；标签、URL、时间（`09:22`）、小数（`1.5`）先占位保护再切。
3. **换行**：不是消息边界，分两种情况。
   - 每一行都很短（≤15 字）：她就是在分行说话，换行一定断条。
   - 否则是长文排版（指标汇报那种一行一个要点）：换行只算弱边界，能不拆就不拆。
4. **最短条长**：一截话攒够 `maxChars × 0.4` 才考虑断开，短的继续并进当前这条，
   免得出现「结论没变」这种四个字一条。
5. **条数上限**（`reply.maxBubbles`，默认 6）：超过就**均匀分组**，不把剩下的全塞进最后一条。
6. **清单 / 汇报整段发**：代码块、多小标题、编号列表、整段长行都整段发。
   这类内容拆开，条目和说明的对应关系就散了。
7. 群聊与私聊的单条上限分开设（`reply.groupMaxChars` / `reply.privateMaxChars`），
   面板「聊天 → 说话的样子（怎么分条）」可调。

## 没做的

- 没有引入第二次模型调用做语义断句。多一次调用就多一次延迟和失败面，
  现有规则已经覆盖「短句不单发、长文不乱切」两个主要问题。真需要时在 `segmentBubbles` 上加一层，
  用 MaiMBot 的校验思路（只允许移动切分位置）就能安全接入。
